Engineering · decisions

Every decision that is load-bearing, and what settled it

Each entry is a choice that could reasonably have gone the other way, the alternative that was rejected, and the measurement or the failure that decided it. These are the parts not to simplify later: most of them look arbitrary until you know what they cost to learn.

1

The premise

Sold on sovereignty and sunk cost, not price-performance

Because

The machines are already bought and idle sixteen hours a day, and the data never leaves the building. Competing on cost per token against a hyperscaler is a race this cannot win and does not need to enter.

Everything downstream follows from it: the owner's pause cannot be overridden, presence gating is strict, and a machine is never taken from the person sitting at it.

Two tiers: harvest and cluster

Because a gang-scheduled job cannot be preempted

Harvest machines may be taken away the moment somebody touches a keyboard. Cluster machines never are. That distinction exists for split work: a job spanning N machines dies if any one yields, and preemption is the entire premise of harvesting.

The alternative - one tier with a priority number - cannot express "this machine will still be here in a minute", which is the only thing an interactive conversation or a pipeline actually needs.

2

Scheduling and presence

No GPU work while anyone is logged in

Measured, not assumed

E2 swept QoS against duty cycle and found every configuration perceptible. The gentlest tested - background QoS at 25% duty - still cost 46% of viewport p95. There is no setting at which a user does not notice, so the answer is none.

Sample presence every 0.5s while active, 5s when idle

The sampling interval is the dominant term in yield latency

E4 measured memory release at ~20ms and model reload at 1-3s. Sampling is cheap; tune this rather than the release path.

Batch work is pulled, interactive work is pushed

A queue suits polling; a conversation does not

Nodes lease batch units when ready. Interactive requests go down a reverse channel the node holds open, so there is no poll interval in the request path.

It also gives the fleet its liveness signal for free: a node holding the channel is available, and one mid-request is neither idle nor gone - conflating those made a healthy node reading a large prompt look like a dead one. 19,243 tokens took 377 seconds, during which the node was answering the whole time.

Capability is measured per workload class, never inferred from the chip

The newer machine is sometimes the slower one

The same two machines differed 7.5% on a 1.5B model and 26.3% on a 7B, and the newer one was slower on one of them. A scheduler that reasons from model names and chip names will be confidently wrong.

3

Splitting a model

Pipeline parallelism, not tensor parallelism

The link is latency-bound, not bandwidth-bound

Pipeline moves one hidden state per token. Tensor parallelism pays roughly two all-reduces per layer per token.

E7 measured the fleet's best link at 0.48 ms (USB gigabit) against Thunderbolt's 0.85 ms for this purpose. The conclusion inverts the intuition the name invites: Thunderbolt is a bandwidth upgrade and would make tensor parallelism slower.

Rank 0 holds the last layers and the output head

The machine that produces a token is the one a scheduler addresses

Ranks are numbered in reverse. Rank 0 answers the request; the others do their share and return nothing anybody reads.

Layer boundaries are accumulated, not multiplied

The obvious formula silently loses a layer

Giving each rank perRank layers starting at (size - rank - 1) * perRank is only correct when every rank holds the same number. With 80 layers over 3 machines the ranks hold 27, 27 and 26 - and layer 26 is owned by nobody. A skipped layer does not fail: the model computes without it and answers fluently from the wrong network.

The model is built with a reduced layer count, not trimmed after loading

MLXNN.Module snapshots its children during init

Removing layers after construction leaves the parameter tree and the KV cache still sized for the whole model. One machine ran twelve layers while being quantised and verified as twenty-four.

Every rank is told what to be; nothing is inferred from the rank number

Implicit agreement survives until somebody renumbers the ranks

Rank, size, listen-or-dial, port, peer address and model all arrive in one dispatch. A dialer with nowhere to dial is refused rather than started.

A split runs where an operator assigned it, never because a request asked

Running a split is a decision about the fleet

It takes machines out of harvesting for as long as it stands, which is why assigning one requires confirmation. Before this, naming a two-machine model in a request would assemble a gang out of any cluster group.

The declaration is the group's serving model, so there is no second switch to keep in step and no way to declare a split for a model that is not one. A model nobody assigned is refused with not-offered: the fleet is not short of anything, what is missing is a decision.

A lost rank fails the request, releases every member, and says so loudly

On a tier defined by never being preempted, this should not happen

Holding the survivors and betting the peer returns costs memory on machines doing nothing, for a bet nothing bounds. Resuming on a replacement needs the lost rank's KV cache, which is not transferable.

Building recovery machinery would be admitting the tier does not work. If ranks are being lost, the answer is to find out why - which requires the failure to be loud rather than absorbed. A silently retried gang failure is how a cluster tier quietly becomes a harvest tier with extra steps.

Harvest loads on request; a cluster holds its model warm

Because a split cannot begin until every rank has built its share

A harvest machine keeps the weights on disk and loads when a request arrives. Somebody is sitting at it, and holding gigabytes for a request that may not come today is what the presence policy exists to prevent.

A cluster machine holds the model loaded. A cold gang pays the slowest machine's load before the first token and pays it again whenever the group falls idle - and the operator already accepted the cost by standing the group up, because it takes those machines out of harvesting for as long as it stands. The memory is spoken for whether or not it holds anything.

The node is told the intent, not the tier. It never learns which groups it belongs to, so a credential living on a workstation does not carry the shape of the fleet - and "hold this loaded" is an instruction it can follow without knowing why.

A machine handed back from a split lets go of the model

Because "handed back" has to be true of the workstation, not only the scheduler

Null from the control plane meant two things. A group that has not been given a model is not an instruction to unload one - a machine configured with a model in its plist must keep it. A machine released from a stood-down split arrives as the same null, and treating them alike left one node holding half a 32B for a group that no longer existed: 9.45 GB on somebody's desk, for a model no socket would route to.

The machine answers it without being told anything new: is what I hold my own, or something I adopted. Releasing constructs a runtime rather than loading one, so the memory goes back immediately and nothing is paid until it is wanted.

4

Groups, tiers and sockets

A socket per group, allocated at creation

The address is the whole of the routing

Nothing in a request names a group, so nothing in a request can name the wrong one. A port is also something you can firewall, monitor and hand to a team.

The rejected alternative - one socket and a group named in the request - makes routing a property of what somebody remembered to send. The rule that must hold alongside it: the port selects which group serves you; it does not establish that you are allowed to. Credentials are still checked per request.

A group that names no model is not a fourth tier

A tier encodes preemptibility, and this differs in neither

Wanting the same machines to run several large models in turn looks like a new kind of group - a "dynamic cluster", loading at user request. It is not. It has the same preemptibility as a cluster group, the same gang admission, the same one-group-per-tier rule and the same rank assignment, and it differs only in whether an operator named the model ahead of the request or left it to the caller. That is a column, not a tier.

So a cluster group with serving_model_id IS NULL serves whichever model it was staged with. The two columns already said the two things: pool_models is what the machines hold, serving_model_id is the one they run - or none, meaning the caller chooses. A fourth tier would have multiplied every rule that mentions tiers, and a machine would have needed to be in three at once.

It serves only what an administrator staged, not the whole catalogue. The promise is then anything I hold, in about a minute - measured at ~40 s for two machines to build their shares of a 32B from disk - rather than a caller waiting twenty minutes for 18 GB to arrive. The cost is that nothing can be pre-warmed, and alternating between two models rebuilds every time: it suits several models used in turn, not two callers wanting different ones at once.

Three things had to change and each was a place that read "no model" as "nothing here". effectiveServing dropped such groups before picking a winner, so the machine was never told it was claimed; warmShareIfAsked released the split share on the next heartbeat, twenty seconds after it was built to answer a request; and releaseIfIdle unloaded only the whole-model runtime and never the share, which was harmless only while the sole groups with an idle window held no share. The agent's own protocol had already written the rule down - servingModel documents that nil means nobody has said, "which is not the same as serve nothing" - and the whole-model path honoured it while the split path did not.

Where a machine's groups disagree, the cluster group wins

Refusing the pair made the order of operations decide the outcome

The first version refused two groups that named different models. That meant assigning a model to a cluster group could fail because somebody had given a harvest group a different one weeks earlier.

The tiers are not equal claims: cluster promises never to be preempted and is the only place a split runs; harvest promises the machine can be taken away. Only one survives on a single machine. What is still refused is a disagreement nothing can resolve - two groups of the same tier.

The serving model belongs to the group and reaches the machine on its heartbeat

A declaration with no path to the machine is not a decision

A node used to run whatever argument its daemon was started with - one plist per box, changed by hand. This fleet ran for a day with a group declaring it served a 14B while its two machines ran a 32B and a 30B, and nothing anywhere disagreed, because nothing was comparing them.

A machine holding part of a split is suspended from harvesting

No machine can promise both

Suspended rather than removed: nothing is written to membership, and the machine is available again the moment the group stops serving that model.

Read from what is assigned, not from what is running - a gang that formed a second after a harvest unit was leased is a gang that dies. The refusal says holding-a-split rather than no-pool, because the machine is in that group and an operator sent to look at membership would find nothing wrong and no explanation.

Standing a group down is not deleting it

Handing machines back should not cost the configuration

A disabled group keeps its machines, model, socket and roles and asserts none of them. Deleting takes its jobs, assignments and roles with it and retires its port so a client left pointing at the old URL cannot quietly reach a different group.

5

Identity and trust

The node key lives in the Secure Enclave, and the HTTP client is NIO

URLSession can only present a SecIdentity

A SecIdentity is a certificate plus a SecKey, and a CryptoKit Enclave key is not a SecKey. Making one would mean storing the key in the keychain, which needs the entitlement and provisioning profile the Enclave route was chosen to avoid. NIO's TLS stack takes a signing callback and does not care where the key lives.

An operator can ask a node to renew; nobody can do it for the node

The Enclave key signs only inside the launchd daemon

dai-agent renew over ssh fails with "unable to sign digest" even as root. So the request rides the heartbeat the node already sends, and the node renews itself. This is also how a machine enrolled before nodes had to trust each other acquires the node CA it needs to join a split.

A renewal is handed to every loop that holds a certificate

Renewal retires the old certificate immediately

This has been wrong twice. The serving loop was missed first and reconnected every five seconds to be refused - loud, at least. The model sync loop was missed next and failed quietly, showing in the console as a machine not holding its models, which reads as a transfer problem rather than a machine locked out by a renewal it performed on itself.

An installer refuses to mint an authority beside an existing fleet

The dangerous branch is the one that reports success

Generating a CA when none is found is right on a new machine and catastrophic next to a database that already holds a fleet: every node's certificate was issued by an authority that lives somewhere else.

The signal is the pairing - no CA here, and nodes there. Neither half means anything alone: an empty state directory is a first install and a populated one is an upgrade, and the installer was looking at only one of them. It now asks the database before writing anything, and offers --adopt-certs, which is also the only path from a working-tree deployment to a packaged one.

A superseded certificate is refused, and unknown states fail closed

A genuine certificate that was really issued is exactly the one nothing else stops

Node states are an allowlist: active, paused and offline are admitted; pending, cordoned and superseded are refused with a reason; anything unrecognised fails closed. A re-enrolled machine's previous identity verifies perfectly and must not work.

6

How things fail

A failed split fails the request, not the node

The first version called fatalError

The reasoning was that a pipeline carrying on with the wrong hidden state answers fluently from the wrong numbers, which is worse than stopping. That is right about continuing and wrong about stopping: on real hardware a peer whose handshake never completed killed the daemon on both machines, took unrelated harvest work with it, and told the control plane nothing. A forward pass cannot throw, so the failure is latched and the caller checks.

A gang ends when a rank fails, with two seconds' grace for the others

A pipeline missing a rank produces nothing

One split failed in ten seconds and the caller waited ten minutes for a machine that had gone away. The grace is long enough that a rank about to report is still named, short enough that nobody waits on a sleeping machine.

A link that goes quiet mid-handshake is given ten seconds, not two minutes

Neither TCP nor TLS reports a peer that simply stops

Both machines sat holding half a model each for the full transport timeout and then said only that the other had not answered. Ten seconds is generous for a link measured in fractions of a millisecond.

A split gives its port back when it ends

A leaked listener does not merely waste a port - it answers

One attempt left its listener bound for the life of the daemon; the next could not bind, and the dialer connected to the corpse of the first and completed a handshake with it. Closing also had to stop waiting out the accept timeout: a listener whose peer never arrived held the port for a further sixty seconds while "closing".

A node that has no pipeline address says so, rather than being remembered

A stale address forms a gang over a cable that is not there

Present-and-null clears it; an absent field leaves it alone, so an older agent is unaffected.

Refusals are named, not just worded

Messages are written to be read and rewritten to be clearer

gang-short, not-offered, group-disabled, holding-a-split. A caller wanting to tell "nobody assigned this" from "the machines cannot reach each other" should not have to match on prose. The Anthropic error shape has no code field, so the name travels in a dai block beside the message.

Every expensive bug here has been silent, and named the wrong thing

Because the error that arrives is rarely the fault that happened

A hardened-runtime Node with no JIT entitlements trapped on the first real program it loaded, and the installer reported that Postgres was unreachable while Postgres was running perfectly well. pkgbuild marked the status app relocatable, so the installer wrote it wherever Spotlight had last seen the bundle id - producing a missing app and permission errors in a build directory, two symptoms of one cause, neither pointing at it, and reporting success. A stop token appended before being checked put <|im_end|> into answers and billed a token for it. A missing layer in a split does not crash at all: the model computes without it and answers fluently from the wrong network.

So each layer is made to report what it did rather than what it was asked to do - layer ranges on a completion, a fingerprint beside a version, layersReported stated rather than inferred from a missing field.

Verify the artifact, not the source

Because a packaging fault is not a property of the repository

No test of this codebase could see a signed binary that cannot execute, an installer that will place a bundle somewhere else, or comments shipped in dist/. They are properties of a file the build produced, so the build takes that file apart: verify-pkg.sh extracts the package, runs the shipped Node, and checks what is inside before calling it built.

It reported the relocation fault on a package that had already been signed, notarised, stapled and installed.

A required field beats a defaulted one where the default is plausible

Because a forgotten optional field is silent and a missing required one is a compile error

enabled was optional on a group, and absent meant enabled - documented as backwards compatibility so callers not yet taught about disabling would behave as they always had. They did not: they behaved as though nothing was ever disabled, which was wrong from the moment the feature landed. Two call sites read the field from the database and dropped it, so a stood-down group went on blocking changes.

Making it required named every construction site at once.

7

Models and storage

Nodes do not reach the hub for weights by default

99 seconds against 3.85

Consulting the hub costs 99s on a model already present on disk, against 3.85s offline - a network round trip per file, on every load, forever. E4 sized the entire preemption design around a 1-3s reload, so this does not merely miss that, it inverts it. The product reason agrees: a fleet sold on data never leaving the building should not have every node fetching from the internet.

A model declares how many machines it needs; the catalogue says so

A repository path tells you nothing

Whether a 40 GB model runs on one machine or two is a decision about the fleet, not a property of the weights. Qwen2.5-14B-Instruct-4bit looks like every other model and is not: serving it engages two machines and takes them out of harvesting.

Residency is compared by size, not by key

A partial transfer counted as holding the model

stored_models ? id only tests that a key exists. A node that had fetched one file of forty reported the model as held. Units differ either side - the node reports GiB, the catalogue bytes - which is its own trap.

What a machine is running is proven by hash, not by version string

A version is a claim the binary makes about itself

Two deploys in one day left both machines on a build from hours earlier, and the only way to find out was to compare file sizes over ssh. The fingerprint is the sha256 of the running executable; the version is what somebody typed. Rollout compares hashes.

8

Open, and deliberately not done

  • Nine mutating admin routes have no authorisation check, including node approval. Not exploitable while only the bootstrap admin can sign in, but an installer's whole job is to create the second user. It needs a fleet-level role, which is a design decision rather than a patch.
  • A machine in both tiers reads as cluster everywhere, including for the presence exemption when serving. See architecture.
  • Builds are not reproducible. Two runs of the release script from one commit produce different bytes, so a checksum verifies a build rather than the build.
  • No /v1/embeddings. The fleet schedules embed work and measures it, but the ANE model produces no usable embedding - see that note.
  • Deleting a group does not yet hold its port back over time, only until the range is exhausted, at which point the longest-retired is reused.
See architecture for what the system is, and testing for which of these claims are held in place by a test rather than by care.
