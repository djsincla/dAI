One command

$ ./scripts/release.sh 0.3.0 --unsigned # or, for something installable elsewhere $ ./scripts/release.sh 0.3.0 \ --app-id "Developer ID Application: Example Inc (TEAMID)" \ --installer-id "Developer ID Installer: Example Inc (TEAMID)" \ --notary-profile dai-notary

In order:

Both suites, with a clock on them

A failure stops the build. So does a suite that stops making progress - it is killed at ten minutes and a stack sample is taken while the process is still there to sample, because that sample is the artifact that identifies a hang and is gone the moment the process is killed.

The agent package

Built with xcodebuild, not swift build: SwiftPM cannot compile MLX's Metal shaders, so a package built that way ships a binary that aborts on the first GPU work unit. Coverage is explicitly off, or the shipped binary tries to write default.profraw next to wherever it is running - a permission error on every start, for a file nobody wants.

The control plane package

npm ci --omit=dev, a TypeScript build, and the official Node runtime staged alongside so Node is not a prerequisite on the target.

Checksums and notes

SHA256SUMS, and a RELEASE.md naming the versions, the schema changes since the previous tag, and any manual step an upgrade needs.

2

Signing

Three credentials, and they are separate things that get confused:

Developer ID Application
signs the binary
Developer ID Installer
signs the .pkg
a notarytool profile
submits to Apple for notarisation

The "Apple Development" certificate that comes with a normal Xcode setup is none of these. It signs code for local use only and Apple will not notarise anything signed with it, so the script checks up front rather than failing after a long build.

Unsigned means local only

Gatekeeper will refuse an unsigned package on every machine except the one that built it, and the failure is silent enough to waste a day. Unsigned builds are for checking that the build works, nothing else.

3

Tags, and why they matter here

$ git tag 0.3.0 && git push origin 0.3.0

Tag as you build. The release notes compute schema changes by diffing control-plane/db/schema.sql against the previous tag, so an untagged repository produces an empty list - and an empty list reads as "nothing will happen to your database" in precisely the place somebody wants the truth before letting an installer near it.

The script asks for the highest tag that is not the one being built. git describe would answer with this release's own tag the moment it exists, then diff the schema against itself and report no changes - the most confident way to be wrong about a database.

4

Two delivery paths

Software reaches a machine two ways, and they are worth telling apart because only one of them involves a package.

PackageSelf-update
What movesthe whole install: daemon, plists, service account, uninstallerone binary
Triggered byinstaller -pkg, usually MDM the control plane, when a pool's desired version changes
Needs signingyesno - it is served over mTLS to a node that already trusts the fleet
Verified byGatekeeper and notarisation sha256 recorded when the build was registered
Rollbackinstall the older package automatic: a machine that does not report in after upgrading puts the previous binary back

In practice a fleet is installed once from the package and updated thereafter by self-update. Both end at the same binary; the fingerprint in the rollout view is what proves it.

5

Upgrading a live fleet

# control plane: install, migrate, restart $ sudo installer -pkg dai-control-0.3.0.pkg -target / $ npm run migrate # re-runnable; the installer also does it # agents: register the build and let the pool converge $ curl -sk -X POST .../admin/v1/agent/builds -d '{"version":"...","path":"..."}' $ curl -sk -X PUT .../admin/v1/pools/id/agent -d '{"channel":"managed","version":"..."}'

schema.sql is written to be re-runnable: every change is IF NOT EXISTS or wrapped in a guard that asks before acting. That is how an upgrade reaches a database that already has data in it, and it is why there is no separate list of migration steps to run in order.

Read the schema section of RELEASE.md first

It lists the statements, not a diffstat - ALTER TABLE pools ADD COLUMN enabled rather than schema.sql | 14 +++-. The first is what is about to happen to your database; the second is a fact about a file.

6

What a checksum does not prove

Two runs of the release script from one commit produce different bytes. Package timestamps, staged file mtimes and a fresh compile each time are all enough on their own.

So SHA256SUMS verifies that the file you have is the file that was built - not that it corresponds to a particular commit. Somebody handed a tag and a checksum cannot confirm they match by rebuilding. That is a real gap and it is written down here rather than discovered by somebody assuming otherwise; closing it means pinned mtimes, SOURCE_DATE_EPOCH and deterministic staging order, which is a piece of work nobody has needed yet.
