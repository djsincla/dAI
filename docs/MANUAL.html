What you get

Two packages. dai-control-version.pkg installs the control plane as a system daemon on one machine. dai-agent-version.pkg installs the agent as a system daemon on every machine that lends capacity. Both are re-runnable and safe on a machine that is currently working.

Part 1

Install the control plane

One machine. Do this first: an agent with nothing to enrol against waits.

  1. Install PostgreSQL

    The one dependency the installer cannot supply. Everything else - the Node runtime, the TLS material, the schema - is in the package or made by it. Version 14 or later.

    First, Homebrew and the command line tools

    On a machine that has never had developer tools, both are needed. The Homebrew installer will offer to fetch the command line tools itself; on a machine with Xcode already installed there is nothing to do. 

    # only if `xcode-select -p` prints nothing
xcode-select --install

/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

    On Apple Silicon Homebrew installs to /opt/homebrew, which is not on the default PATH. The installer prints the two lines to fix that; they are repeated here because skipping them is the usual reason brew: command not found appears in a new shell. 

    echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
eval "$(/opt/homebrew/bin/brew shellenv)"
brew --version                       # prove it before going on

    The control plane package does not need Homebrew. It carries its own Node runtime. Homebrew is here only to install and supervise PostgreSQL, so a site that already runs Postgres another way can skip all of this.

    Then PostgreSQL, native under launchd - the recommended way

    No container runtime, no licensing question, and the same start-at-boot mechanism the control plane itself uses. 

    brew install postgresql@17
sudo brew services start postgresql@17

    Plain brew services start is not enough, and the difference is invisible until you reboot. Run as your user it installs a LaunchAgent, which starts when you log in. The control plane is a LaunchDaemon and starts at boot. A machine that reboots unattended comes up with a control plane that cannot reach its database, and the failure looks like the fleet rather than the database.

    sudo brew services start puts it in /Library/LaunchDaemons, which is right, and then two things go wrong that are worth knowing before they happen rather than after.

    Fixing what sudo brew services leaves behind

    It writes the plist without a UserName, so launchd runs the server as root and PostgreSQL refuses: "root" execution of the PostgreSQL server is not permitted. With KeepAlive set it then retries forever, filling the log.

    And it writes the plist root:admin, where launchd requires root:wheel for anything in /Library/LaunchDaemons. The symptom is Bootstrap failed: 5: Input/output error, which says nothing about ownership. 

    sudo plutil -insert UserName -string $(whoami) \
  /Library/LaunchDaemons/homebrew.mxcl.postgresql@17.plist
sudo chown root:wheel /Library/LaunchDaemons/homebrew.mxcl.postgresql@17.plist

    Then reload it with a bootout that waits. launchctl bootout is asynchronous: it returns when the job has been asked to stop, not when it has stopped, and bootstrapping into a label that still exists fails with the same 5: Input/output error. Until the old job is really gone, launchd keeps running the definition it cached - so a corrected plist on disk changes nothing and every symptom stays identical.

    sudo /usr/local/libexec/dai-control/reload-daemon.sh \
  system homebrew.mxcl.postgresql@17 \
  /Library/LaunchDaemons/homebrew.mxcl.postgresql@17.plist

    The helper ships with the control plane and is not specific to it.

    Prove it, twice

    psql -h localhost -p 5433 -d postgres -c 'select 1'
ps -o user= -p $(pgrep -f "bin/postgres" | head -1)   # must not be root

# the property that actually matters: launchd restarts it
sudo kill -9 $(pgrep -f "bin/postgres" | head -1)
sleep 5 && pg_isready -h localhost -p 5433

    Verify that launchd restarts the server, not merely that a process is present. A server that runs until something stops it does not satisfy the requirement.

    Choosing the port

    The fleet's URL names 5433. Set port = 5433 in /opt/homebrew/var/postgresql@17/postgresql.conf rather than changing the URL, and nothing else - plist, scripts, notes - has to change. If you are migrating from an existing database, run the new server on a spare port first, prove it, and move it to 5433 only when the old one is stopped.

    Creating the role and database

    Only needed if you are restoring a dump. For a new fleet the installer creates both. 

    psql -h localhost -p 5433 -d postgres -c "create role dai login password 'dai' superuser"
psql -h localhost -p 5433 -d postgres -c "create database dai owner dai"

    If you would rather use a container

    control-plane/docker-compose.yml brings up postgres:17-alpine on 5433. It carries a named volume and restart: unless-stopped; both are required for production use. Note that a restart policy only acts once the container runtime is running, so the runtime itself must start at login or boot - which is the fragility the native install avoids.

    Docker Desktop is separately licensed above a small-business threshold, while the Engine and CLI are Apache-2.0. Apple's container is a native alternative but has no compose support. For the database holding fleet state, the native install has fewer dependencies.

  2. Install the package

    sudo installer -pkg dai-control-0.8.11.pkg -target /

    This lays down a bundled Node runtime, the server, the schema and the helper scripts under /usr/local/libexec/dai-control. It starts nothing.

  3. Configure and start it

    sudo /usr/local/libexec/dai-control/install.sh \
    --db postgres://dai:dai@localhost:5433/dai \
    --hostname control.example.com

    This generates TLS material if absent, applies the schema, writes the launch daemon and starts it. It prints the console address and the CA certificate path the agents will need.

    Keep the CA path it prints. Every agent needs that file. The fleet issues its own certificates, so the system trust store does not know them, and the alternative to distributing the CA is disabling validation - which would also accept anything else on that address.

  4. Sign in and change the password

    Open https://hostname:8452/ui/ and sign in as admin / admin. It will make you choose a password before anything else works.

    The bootstrap account is created on every start, but only when no account has a password. It cannot resurrect itself on an established fleet and cannot undo a password change.

Restricting who can reach what

Four surfaces share port 8452 and each takes its own CIDR allow-list, set in the daemon's environment. /monitor/v1 is closed entirely unless a CIDR is configured - the alternative is a long-lived secret in a scraper config that nobody rotates.

VariableGuardsEmpty means
DAI_AGENT_CIDRS/agent/v1any address (mTLS still required)
DAI_ADMIN_CIDRS/admin/v1any address (credential still required)
DAI_MONITOR_CIDRS/monitor/v1closed
Part 2

Add a machine

One package for every site. What differs between machines is a single configuration file.

  1. Mint a join token

    In the console: Machines → Add a machine. Choose how long it should be valid for, add a note if you want one, and mint it.

    The token is shown once. The control plane keeps only enough to recognise and revoke it, so the listing shows the first eight characters and nothing more. Copy it before closing the drawer.

    Or from a script:

    ./scripts/dai-fleet token --hours 24
# or POST /admin/v1/join-tokens {"expiresInHours": 24}

    Tokens expire and are best minted one per machine: withdrawing one is then a decision about one machine rather than about all of them. The same drawer lists existing tokens with their expiry and revokes any of them.

  2. Write the config on the new machine

    At /Library/Application Support/dAI/config.json, with the CA certificate beside it:

    {
  "url": "https://control.example.com:8452",
  "joinToken": "…",
  "caPath": "/Library/Application Support/dAI/server-ca.crt"
}

    Optional keys worth knowing: model pins what this machine serves, aneModel points at a Core ML embedder, and pipelineInterface names the interface used for split traffic.

  3. Install the package

    sudo installer -pkg dai-agent-0.8.11.pkg -target /

    The daemon starts, generates a key inside the Secure Enclave, signs a certificate request with it and enrols. The private key never leaves the Enclave, so copying the disk does not copy the identity.

    Enrolment happens in the daemon rather than the command line tool, because the Secure Enclave requires an unlocked keybag. dai enroll run as a signed-in user cannot do it and reports so.

  4. Approve it

    ./scripts/dai-fleet pending
./scripts/dai-fleet approve studio-01

    Or from the console's Machines page. Until approved, a machine is enrolled and idle.

  5. Give it tiers, a group, and weights

    A correctly added machine looks idle for a long time. It needs to be in a pool, and it needs the model files, which are transferred by the agent and take as long as ~18 GB takes on your network.

    ./scripts/dai-fleet versions   # what each machine runs

Harvest or cluster. A harvest machine is somebody's workstation and is handed back the moment they touch it. A cluster machine is dedicated and never preempted, which is what interactive serving needs: a conversation needs a model that is still resident a minute from now, and the harvest tier cannot promise that by design. A machine may be in both.

Part 3

Everyday operations

Is it working?

curl -sk https://localhost:8452/healthz
{"ok":true,"surface":"both","version":"0.8.11"}

Then the machines. The three fields that matter are on one line:

curl -sk https://localhost:8452/admin/v1/nodes \
  -H "authorization: Bearer daik_…" | python3 -m json.tool
FieldMeansWatch for
servingholding the dispatch channel open false = cannot be routed to, whatever else is true
presenceStatewhether somebody is at it drives the completion cap
residentModelsloaded in memory now not the same as on disk
lastHeartbeatseconds since it spoke >120s and it drops out of routing

residentModels and stored models are different facts. Resident is what a runtime holds in memory; stored is what is on disk. Reading one for the other has cost this project an afternoon more than once. "Nobody is serving this" and "nobody has the weights" need different actions.

Authenticating a script

The console covers everything below. The API is shown because it is what a script uses and what can be pasted into a ticket. 

TOK=$(curl -sk https://host:8452/admin/v1/auth/login \
    -H 'content-type: application/json' \
    -d '{"username":"admin","password":"…"}' | jq -r .token)

curl -sk https://host:8452/admin/v1/nodes -H "authorization: Bearer $TOK" | jq
curl -sk https://host:8452/monitor/v1/health   # from a permitted range

/monitor/v1/health answers 503 when a group has a socket that nothing is listening on, naming the group and the port. That case is otherwise invisible: the group exists, its models are assigned, its machines hold them, and nothing answers.

Machines

A newly enrolled machine is pending and runs nothing until approved. 

curl -sk -X POST https://host:8452/admin/v1/nodes/{id}/approve \
    -H "authorization: Bearer $TOK" -d '{}'

An operator's pause is administrative and liftable. The machine owner's pause is not: there is no administrative control for it, and the console shows a disabled label rather than a button that would not work.

A machine offering both tiers reads as cluster everywhere, including for the presence exemption when serving. An interactive request can therefore land on it while somebody is using it. Give a workstation only the harvest tier if that matters.

Groups

A new group is allocated a socket immediately, bound before the response is sent. The port is in the response and on the group's card. Applications select a group by connecting to that port; nothing else selects one. 

curl -sk -X POST https://host:8452/admin/v1/pools \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"name":"split-cluster","tier":"cluster"}'
{"id":"…","name":"split-cluster","tier":"cluster","servingPort":8461}

Creating a cluster group sets schedule = gang and preempt = never automatically. A cluster group admits only cluster-tier machines; a harvest group admits any machine.

Groups created before sockets existed are not given one during an upgrade. Request it once: 

curl -sk -X PUT https://host:8452/admin/v1/pools/{id}/socket \
    -H "authorization: Bearer $TOK"
{"servingPort":8460,"allocated":true}

Standing a group down - reversible

A disabled group keeps its machines, model, socket and roles and asserts none of them. It decides nothing about what its machines serve, suspends nobody, hands out no work, forms no gangs, and refuses on its own socket with group-disabled. The response lists the affected machines and what each will serve instead. This is how a cluster group's machines are returned to their harvest group without dismantling anything. 

curl -sk -X PUT https://host:8452/admin/v1/pools/{id}/enabled \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"enabled":false}'

Deleting a group - not reversible

Its jobs and their work, its model assignments and every role on it are deleted with it. Its machines are freed. Its socket is retired rather than reused, so a client left pointing at the old port cannot reach a different group. Without confirm=true the call refuses and reports what would be lost; read that before repeating it.

curl -sk -X DELETE "https://host:8452/admin/v1/pools/{id}?confirm=true" \
    -H "authorization: Bearer $TOK"

Serving a model

Assign the model to a pool, then point the pool at it. The agents transfer the weights themselves and report holding them. 

PUT  /admin/v1/pools/{poolId}/models/{modelId}   # stage it
PUT  /admin/v1/pools/{poolId}/serving-model            # serve it
GET  /admin/v1/pools/{poolId}/models                   # heldBy / loadedOn

Holding is not loading

PUT /pools/{id}/models/{modelId} declares that every machine in the group should hold these weights. A machine holds many models and serves one. PUT /pools/{id}/serving-model is the call that reaches the machines: each learns it on its next heartbeat and swaps its runtime, releasing the previous model's weights.

Setting serving-model to null means nobody has said, which is not an instruction to unload. Machines keep serving what they have.

Declaring a model's shape

How many machines it runs across. Checked at assignment, so a two-machine model assigned to a one-machine group is refused with a message rather than discovered at dispatch as a hang. 

curl -sk -X PUT https://host:8452/admin/v1/models/{id}/shape \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"machines":2}'

Splitting a model across machines

In the console this is serve a model on a cluster group's card, and the field is "Across how many machines". Nothing in the interface uses the word split; the card reports the result as "across 2 machines". The link appears only on cluster groups, because a harvest group's machines are preemptible and a split rank cannot be preempted.

Four conditions must hold. The fleet reports which one does not.

ConditionHow
The model declares more than one machine PUT /models/{id}/shape {"machines":2}
A cluster group is serving it PUT /pools/{id}/serving-model, confirm: true
The machines can reach each other DAI_PIPELINE_INTERFACE in the agent's plist. The split link is deliberately not the one used to reach the control plane. A node whose link is down reports no address, and a gang with nowhere to dial is refused in milliseconds.
All of them are connected at once A gang is admitted whole or not at all. A model using every machine in its group leaves no spare rank, so any other request in flight - including a token count - blocks it.

The confirmation on serving-model is not a formality: it names the machines that stop being available to their harvest group for as long as this stands. Ask on the group's own socket, and both machines log their share: 

curl -sk https://host:8461/v1/chat/completions \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"max_tokens":40,"messages":[{"role":"user","content":"hello"}]}'

rank 0 (layers 24..<48) finished 205 tokens in 15.4s

The answer comes from rank 0, which holds the output head.

Agent versions

A pool is either managed, where the control plane hands out the binary and machines self-update, or external, where it records what it expects and never acts. External is what makes it safe to run beside an MDM: two systems racing to own one executable is worse than either owning it alone. 

# register a build from a file on the control plane's disk
curl -sk -X POST https://host:8452/admin/v1/agent/builds \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"version":"0.8.11","path":"/path/to/dai-agent"}'

# tell a pool which one to run
curl -sk -X PUT https://host:8452/admin/v1/pools/{id}/agent \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"channel":"managed","version":"0.8.11"}'

# watch it converge; upToDate compares hashes, not version strings
curl -sk https://host:8452/admin/v1/agent/rollout -H "authorization: Bearer $TOK" | jq

Read the fingerprint, not the version. The version a node reports comes from its plist and can remain stale after a self-update. The fingerprint is the hash of the running executable. Machines pick up a new build within 120 seconds.

Idle unload and prompt cache

Two per-group numbers, on the group's tuning link in the console or by API. Both follow the fleet unless the group overrides them, and clearing a field returns it to the fleet's value rather than setting zero.

KnobDefaultWhat it decides
idle-unload300s How long these machines hold a model once nothing is being asked of them.
prompt-cache8 GB Memory each machine may keep for warm conversations. The machine clamps this to what it can afford.
 
curl -sk -X PUT https://host:8452/admin/v1/pools/{id}/idle-unload \
    -H "authorization: Bearer $TOK" -d '{"seconds":600}'   # null for the default

A cluster group pinned to a model has no idle window, and the console disables the field and says so. Dedicated means loaded, so a window would describe a release that never happens. An unpinned cluster group does have one: it holds whatever it was last asked for, and without a window the first caller's model stays in memory for as long as the group stands.

Certificates

Certificates last thirty days and renew automatically at two thirds of life. A certificate cannot be renewed for a node from elsewhere: the key lives in the Secure Enclave and signs only inside that machine's daemon, so dai-agent renew over ssh fails even as root. The control plane can ask the machine to renew. 

curl -sk -X POST https://host:8452/admin/v1/nodes/{id}/renew \
    -H "authorization: Bearer $TOK" -d '{}'
./scripts/dai-split prepare mlx-community/Qwen2.5-Coder-32B-Instruct-4bit --machines 2
./scripts/dai-split up
./scripts/dai-split status
./scripts/dai-split down

A split runs as a gang: every rank is admitted together or none is. Half a pipeline is not a slower answer, it is a request that hangs while holding memory on machines that could have been doing something else.

Giving a machine back temporarily

POST /admin/v1/nodes/{nodeId}/pause
POST /admin/v1/nodes/{nodeId}/resume

The owner's pause applies on every tier and has no override. A dedicated box is still somebody's machine.

Proving the backup, and the empty-server path

Both procedures below have been tested against a throwaway PostgreSQL instance on a spare port, leaving production untouched. 

# a server with no dai database at all, which is the real starting state
docker run -d --name dai-restore-test \
  -e POSTGRES_USER=dai -e POSTGRES_PASSWORD=dai -e POSTGRES_DB=postgres \
  -p 5439:5432 postgres:17-alpine

# what the installer does: creates the database, applies the schema
DATABASE_URL='postgres://dai:dai@localhost:5439/dai' \
  /usr/local/libexec/dai-control/node /usr/local/libexec/dai-control/dist/migrate.js
# created database dai
# schema applied; 25 tables

# then restore a dump over it and count what came back
gzcat dai-20260830.sql.gz | docker exec -i dai-restore-test psql -U dai -d dai
docker exec dai-restore-test psql -U dai -d dai -tAc \
  "select count(*) from nodes"

docker rm -f dai-restore-test

The empty-server path needs nothing but the URL. migrate.js creates the database if it is missing, applies all 25 tables, and seeds the admin account with a forced password change. So a brand new deployment needs a reachable Postgres server and nothing prepared inside it.

Backing up

The database holds node identities, the certificate authority, every machine's certificate, pools, models and work records. If it is lost, agents present certificates the control plane no longer recognises and every machine must be enrolled again. 

pg_dump postgres://dai:dai@localhost:5433/dai \
  | gzip > dai-$(date +%Y%m%d).sql.gz

Run this on a schedule. If PostgreSQL runs in a container without a named volume, this dump is the only copy of the fleet's state.

The uninstaller never touches the database, with or without --purge. Removing it is a decision made deliberately, with a database tool.

Part 4

Upgrading

The control plane: two commands

sudo installer -pkg dai-control-0.8.12.pkg -target /
sudo /usr/local/libexec/dai-control/install.sh

The second command is not optional. The package puts new code on disk and does nothing else: it does not apply the schema and it does not restart the daemon. Install it alone and the old process keeps serving until something restarts it - and when something does, the new code meets the old database and refuses every request with a message naming a column it expects and cannot find. This failure has occurred in practice.

install.sh needs no arguments on a machine that is already installed. The database URL, port and network rules are read back out of the installed plist, and the TLS material is left alone because an authority already exists. A flag still wins if you give one, so a value can be corrected without reinstalling.

Expect a few seconds of downtime: agents' channels drop and reconnect, and any in-flight question fails.

The agents: register, then repoint

./scripts/dai-fleet release 0.8.12 --binary dist/0.8.12/dai-agent-0.8.12.pkg

Then point every pool at the new version, including stood-down ones. A pool left on the old build will pull machines back to it.

Do not install the agent package by hand. The updater reverts it to whatever the pool asks for, in about a second. An agent log once read upgrading to 0.7.0 one second after a 0.8.0 install. Deploying an agent means registering a build.

Verifying

curl -sk https://localhost:8452/healthz          # control plane version
./scripts/dai-fleet versions                     # each machine, against target
Part 5

When it goes wrong

Every failure seen on this fleet so far, and what it actually was. The pattern is worth naming: each one failed quietly and blamed the wrong component.

A request was refused

All of these are 503 with a code. On the OpenAI surface it is error.code; on the Anthropic surface, whose error shape has no such field, it is error.dai.code.

CodeMeansAction
no-nodes No active node is holding the reverse channel. Check the machines are up and approved. If they heartbeat but do not serve, the agent is reconnecting - read the node log.
all-in-use Every node has a user present, so GPU work is not permitted. Nothing. This is the policy working. It resolves when somebody locks their screen.
no-capacity-for-kind No node can run this kind of work at all. Usually a machine with no GPU model configured being asked to generate.
not-offered The model runs across machines and no cluster group serves it. PUT /pools/{id}/serving-model with confirm: true. What is missing is a decision, not a component.
gang-not-cluster A split needs cluster-tier machines and none connected is one. Give the machines the cluster tier. A split rank cannot be preempted, so this model cannot run on harvest hardware.
gang-short The group cannot field the machines the model needs, or they cannot reach each other. Check they are all connected, then that each has said where peers should dial it (DAI_PIPELINE_INTERFACE). A node whose link is down reports no address.
group-disabled The group whose socket you are using has been stood down. PUT /pools/{id}/enabled, or use another group's port. The listener stays bound deliberately: a refused connection would be indistinguishable from a control plane that had fallen over.
node-unreachable A gang formed and broke. The message names every rank and what each said. Read the ranks. The one that stayed silent usually caused it.

A machine is not taking work

The node's log reads asked for embed, generate, got none: <reason>.

ReasonMeans
emptyThere is no work. The fleet is idle.
none-of-these-kinds There is work, but not of a kind this machine may run now - almost always GPU work while somebody is at the keyboard.
no-pool There is work, and this machine is in no group that can be given it.
node-pausedAn operator paused it. Liftable in the console.
user-paused The machine's owner paused it. Not liftable by anyone else, deliberately.
holding-a-split This machine's cluster group is serving a model that runs across machines, so it is unavailable to its harvest group. It returns on its own when that group stops serving the model.

holding-a-split is reported separately from no-pool because the machine is in that harvest group. An operator sent to check membership would find nothing wrong and no explanation.

A machine cannot talk to the control plane

MessageMeansAction
no client certificate The request arrived without one. Usually something other than an agent talking to the agent surface.
unknown certificate The fingerprint is not in the fleet. If it follows a renewal, a loop in the daemon is still presenting the old certificate. Restart the daemon and report it; this is a bug and has occurred twice.
node not approvedEnrolled and waiting. Approve it.
superseded The machine re-enrolled and this is the older identity. It verifies correctly, which is why it is refused. Re-enrol, or point the daemon at the current identity.
certificate revokedWithdrawn deliberately. Re-enrol if that was not intended.
certificate expired Past thirty days with no renewal. Re-enrol. An expired certificate cannot authenticate, so the machine cannot be asked to renew and the console offers no control.
node cordonedHeld out of the fleet by an operator. Uncordon it.

A split will not run

Read both machines' logs; the two halves usually report different things.

# a working split, on both machines
rank 0 listening on 7710
pipeline: a peer connected from 192.168.99.2
pipeline: handshake completed with 192.168.99.2
rank 0 (layers 24..<48) finished 205 tokens in 15.4s
In the logMeans
no handshake with … after 10s TCP connected and TLS never proceeded. Almost always the peer going away mid-handshake.
bind: Address already in use A previous split left its listener bound. Fixed in 2026.08.13-6; if seen, the machine is running something older.
the other machine did not answer within 120s The ranks paired and one never produced its tensor. Usually a machine loading its half under load.
rank N could not hand its hidden state on The link broke mid-generation. The other rank's message says from which end.
did not report before the gang was released This rank said nothing within two seconds of another rank failing. Usually the machine that caused the failure.

The split link is not the control plane's link. A split runs over whatever the machines share - a Thunderbolt bridge, for example - while both reach the control plane over the LAN. A bridge goes inactive when its peer sleeps or is unplugged, the advertised address stops being reachable, and the node clears it on the next heartbeat.

Nothing is wrong and nothing is happening

  • A machine reads as suspended. Its cluster group is serving a split model; the capacity is deliberately withdrawn.
  • A model is listed but every request is refused. The catalogue says a node holds it; routing says no node is free this instant. A node reading a large prompt is occupied for minutes and is not parked on the channel.
  • A group shows "not serving this group's model". The machines are running something else - either they have not taken the group's model yet, or a cluster group is overriding this one. The card names which.
  • A node is not holding what it was assigned. The drawer shows the reason under "Not holding", reported on every beat, so it is current rather than stale.
  • Health says 503 with a group name. That group has a socket nothing is listening on. This is the dangerous case, because the group otherwise looks healthy.

no active nodes are connected

No machine is holding a dispatch channel. Check serving in the node list, not state or lastHeartbeat.

  • Asleep. The commonest cause by far. Wake it, or stop it sleeping.
  • Busy. A machine mid-generation is not polling. A 30s cold load plus a 45s answer is 75 seconds of looking absent.
  • Paused. The owner's pause, which has no override.

column "…" does not exist

New code, old database. You installed the package without running install.sh. Run it now; it is safe on a running machine.

Every request goes to the same machine

Expected, if the others are busier, less free, or lack the model. The router orders candidates: least busy, then freest of its owner, then holds the model, then measured throughput, then longest since it was last given work.

If it is the wrong machine - the one somebody is sitting at - check that the others are serving=true. A machine that is asleep or paused is not a candidate at all, and no preference can pick it.

Answers stop mid-sentence

Presence policy, not max_tokens. Read dai.maxTokensApplied and dai.cappedByPolicy in the response. A machine somebody is using allows 256 tokens; locked allows 2,048 and logged out 4,096. Raising the request limit changes nothing - the answer has to land on a freer machine.

The first answer takes 30 seconds, the rest are instant

A cold model load, or a prompt-cache miss. Both are normal. The cache keys on longest common prefix, measured at 34.6s cold against 0.8s warm, which is why a repeated question is fast and a changed one is not.

If it happens repeatedly, the model is being unloaded between questions: look at the pool's idle-unload window.

A machine holds the model and never loads it

Residency follows dispatch. Until the machine is given work, it holds weights and loads nothing. Check heldBy against loadedOn in GET /admin/v1/pools/{poolId}/models.

brew upgrade postgresql@17 refuses

sudo brew services start takes root ownership of several Homebrew paths, and warns as it does so. Later upgrades and reinstalls of that formula then fail until those paths are removed by hand. 

sudo rm -rf /opt/homebrew/opt/postgresql@17 \
            /opt/homebrew/var/homebrew/linked/postgresql@17
brew upgrade postgresql@17

This is a consequence of supervising PostgreSQL as a system daemon rather than a per-user service, which is required for it to start at boot.

Nothing works after a reboot

Check the database first. The control plane is a launch daemon and starts itself at boot; whether its database does depends entirely on how Postgres was installed. 

psql postgres://dai:dai@localhost:5433/dai -c 'select 1'
ps -o user= -p $(pgrep -f "bin/postgres" | head -1)
  • Native, as a LaunchDaemon in /Library/LaunchDaemons: starts at boot, no login needed. This is the arrangement to want.
  • Native, as a LaunchAgent in ~/Library/LaunchAgents: starts only when that user logs in. A machine that reboots unattended comes up with no database.
  • In a container: needs the runtime to start on its own and a restart policy on the container. A restart policy alone does nothing if the runtime is not running.

In each case the control plane is running but cannot serve requests.

Where to look

# on a machine that lends capacity
/var/log/dai/agent.log              # heartbeats, work, serving, splits
/var/log/dai/updater.log            # self-update, every 120s

# on the control plane
/var/log/dai-control/               # when installed as a daemon
GET /admin/v1/agent/upgrades        # what each machine tried, and how it ended
GET /monitor/v1/metrics             # Prometheus exposition

The node drawer in the console carries the same facts: chip, working set, headroom, presence, agent version and fingerprint, certificate expiry, why it is not holding something, and recent activity. It is readable by that machine's owner whatever their role, so an unrelated slowdown can be checked rather than assumed to be the agent.

Part 6

Giving a machine back

sudo /usr/local/libexec/dai/uninstall.sh            # keeps the identity
sudo /usr/local/libexec/dai/uninstall.sh --purge    # enrol it again later

Without --purge, the machine keeps its Secure Enclave key and certificate, so reinstalling rejoins the same fleet as the same node. With it, the identity is destroyed and the machine must be enrolled and approved again.

Revoke from the control plane too, or the fleet will keep a certificate it should not honour: 

POST /admin/v1/nodes/{nodeId}/revoke

Cluster machines are exempt from the gate, not from the preference. A cluster machine serves whatever its presence, because interactive work needs it to. But the router still prefers the freest machine available, so work moves to the one nobody is using - and the completion cap still follows the presence of whichever machine answers.

Words that mean something specific

harvest
A tier. Somebody's workstation, handed back the moment they touch it.
cluster
A tier. Dedicated, never preempted. What interactive serving needs.
presence
Whether somebody is at a machine, derived from input idle time, screen lock and console ownership. Drives what the machine may do.
resident
Loaded in a runtime, in memory, now. Not the same as stored.
stored
On disk. A machine can hold 18 GB of weights and be serving none of it.
gang
The set of machines running one split model. Admitted whole or not at all.
group / pool
A set of machines with a socket of their own and a model they serve.
dispatch
One unit of work handed to one machine. Nothing streams: a completion goes as one unit so that preemption has a bounded worst case.
