Operator guide

Installing and running a dAI fleet

Superseded in part by the installation and operations manual. This guide predates the join-token API and the native PostgreSQL install, and still shows join tokens being created with psql. Prefer the manual for installation, upgrading and database setup.

Standing up the control plane, putting an agent on a Mac, and running the fleet day to day. Written for whoever operates the fleet, not for the people whose machines are being borrowed.

Before you begin

Four things that will surprise you

Read these first. Each one has already cost somebody an afternoon, and three of them look like failures when they are not.

Build with xcodebuild, never swift build

SwiftPM cannot compile MLX's Metal shaders. A binary built with swift build installs fine and then aborts from C++ the first time it touches the GPU, looking exactly like a missing Metal toolchain. The installer refuses a build it does not recognise for this reason.

The machine enrols itself, the installer does not

Generating a key in the Secure Enclave needs a session whose keybag is unlocked, which an SSH session does not have even as root. So enrolment happens in the daemon on first start. Over SSH you will see ==> the daemon will enrol on first start. That is the normal path, not an error.

Two steps have no interface yet

Creating a join token is a direct database insert, and approving a machine is a curl call. There is no button for either. Both are shown below; neither is hidden from you, but neither is finished.

These steps have not been run end to end on a clean machine

The commands here are taken from the scripts as they currently stand, and the fleet's existing machines were installed before several fixes landed. Expect to hit something. The troubleshooting section covers every failure seen so far.

You will need:

  • A Mac to run the control plane, with Docker and Node.
  • Xcode with the Metal toolchain, on whichever machine builds the agent.
  • Administrator access on every Mac that will join the fleet.
  • Apple Silicon on the fleet machines. There is no Intel path.

Part 1

Install the control plane

One per site. It holds the certificate authority, the work queue, the model catalogue and the console, and it should live on a machine that stays on.

Start the database and generate a certificate authority

# in control-plane/ npm install npm run db:up # postgres on port 5433 ./scripts/make-certs.sh # CA, server and node certificates

This creates certs/ca.key, which is the single most important file in the system. Every node certificate traces back to it, and enrolment needs the Secure Enclave, so losing it means visiting every machine in person to enrol again. Back it up before you go further.

Start the server

DATABASE_URL=postgres://dai:dai@localhost:5433/dai \ DAI_MODEL_REPO=$PWD/models \ PORT=8452 \ npm start

It should log [both] mTLS on https://localhost:8452. If it says HTTP on :8452 (no TLS material...) the certificates were not found, and you have an unauthenticated dispatch endpoint. Stop and fix that rather than carrying on.

Write the configuration down

Those environment variables exist only in the shell that launched the server. Restarting it later without them has already turned into archaeology once. Put them in a file you keep, and take a backup, which captures them along with the CA and the database:

DATABASE_URL=postgres://dai:dai@localhost:5433/dai ./scripts/backup.sh

The archive is around a megabyte. It holds the CA private key in the clear, so it belongs somewhere with fewer readers than the machine it came from.

Get your console credential

DATABASE_URL=postgres://dai:dai@localhost:5433/dai node scripts/token.mjs # ADMIN=dd221cb9-1658-4c90-a3b2-93ca86cf1346

Open https://localhost:8452/ui/, accept the certificate warning (it is your own CA), and paste that value into the session field in the sidebar.

This credential is a user id, not a password

It is the primary key of the users table, sent as a bearer token. There is no password, no expiry and no revocation short of deleting the user. The same id appears in the jobs list and the audit log, so anyone who reads it anywhere gets full administrative access. Acceptable for machines you own; not acceptable once somebody else's Mac joins.

Part 2

Deploy an agent to a Mac

Repeat per machine. Steps 1 and 3 are done once for the whole fleet; the rest are per machine.

Build the agent

# in agent/ — xcodebuild, not swift build xcodebuild build -scheme dai-agent -destination 'platform=OS X' \ -configuration Release -derivedDataPath .xcbuild \ ENABLE_CODE_COVERAGE=NO CLANG_ENABLE_CODE_COVERAGE=NO \ SWIFT_ENABLE_CODE_COVERAGE=NO

Products land in .xcbuild/Build/Products/Release: the dai-agent binary, dAI.app for the menu bar, and several .bundle directories that must travel with the binary or it dies on first use.

Check the machine can run it

sudo /path/to/dai-agent preflight

Run it with sudo. The daemon runs in session 0, which is a different enough context that checking only the interactive case proves less than it looks like. You want READY. This machine can run the agent as a daemon.

Create a join token

# no API for this yet, so insert it directly docker exec control-plane-postgres-1 psql -U dai -d dai \ -c "insert into join_tokens (token) values ('studio-01-join')"

A token gets a machine into the pending queue and nothing more. It is consumed when the certificate is collected, and the agent deletes its copy afterwards so it cannot be replayed to enrol a second machine.

Copy the files to the machine

ssh studio-01.local 'mkdir -p dai/bin dai/packaging' scp .xcbuild/Build/Products/Release/dai-agent studio-01.local:dai/bin/ scp -r .xcbuild/Build/Products/Release/*.bundle studio-01.local:dai/bin/ scp -r .xcbuild/Build/Products/Release/dAI.app studio-01.local:dai/bin/ scp packaging/*.sh packaging/*.plist.in studio-01.local:dai/packaging/ scp ../control-plane/certs/ca.crt studio-01.local:dai/srv-ca.crt

Run the installer

ssh -t studio-01.local "sudo ~/dai/packaging/install.sh \ --url https://192.168.4.24:8452 \ --token studio-01-join \ --ca ~/dai/srv-ca.crt \ --ane ~/dai/models/ane_embed.mlpackage \ --build ~/dai/bin"

--build is required on every machine except the one that compiled the binary. --model is optional: a machine with no GPU weights is a normal machine that does embedding work, and the smallest Macs in a fleet are usually exactly that.

Expected, not an error

==> the daemon will enrol on first start is the normal outcome over SSH. The installer tries enrolment as a convenience and the Secure Enclave refuses; the daemon does it properly a moment later.

Approve the machine

The machine now appears as pending and does nothing until a human lets it in. Find it and approve it:

docker exec control-plane-postgres-1 psql -U dai -d dai -t -A \ -c "select id, hostname from nodes where state='pending'" curl -sk -X POST https://localhost:8452/admin/v1/nodes/NODE_ID/approve \ -H "authorization: Bearer ADMIN_ID" \ -H "content-type: application/json" -d '{}'
No approve button yet

The console lists machines but has no control for approving one. The API endpoint is the only way today.

Confirm it joined

Open the console. The machine should appear under Machines with a presence state and a heartbeat. If it enrolled under a name you do not recognise, see the troubleshooting table.

Part 3

Operating and monitoring

The console is at https://localhost:8452/ui/ and has five views. Overview is the one to leave open.

ViewWhat it answers
Overview What needs attention right now, and eligible capacity over time. Drag the chart sideways to change the span, from ten minutes to three days.
Machines Every machine, its presence, what it will accept, and what it is serving. Groups sit above the table; drag a machine between them.
Models What the fleet is supposed to hold against what it does. Add a model, push it to a group, inspect placement per machine.
Deployment What agent version each machine runs, and who is allowed to change it.
Logs Machine activity and fleet actions as one sequence, searchable, exportable as text or HTML.

Reading the Overview

The attention list is ordered by what blocks what. A decision waiting on a human comes first, because nothing behind it moves until somebody acts. Problems come next. An owner's pause appears as information rather than a warning: it is a right they were given, and it is not yours to lift.

Putting a model on machines

Models already on the control plane's disk import without downloading anything, which is the cheapest path and the one the Add model list shows first. Import hashes every file, so a truncated copy cannot pass as good.

DAI_SESSION=ADMIN_ID node scripts/import-model.mjs \ ~/Library/Caches/models/mlx-community/Qwen2.5-7B-Instruct-4bit \ --id mlx-community/Qwen2.5-7B-Instruct-4bit \ --runtime mlx --kind generate --context 32768 --quant 4bit

Then push it to a group from the Models view. Pushing moves no bytes: it records a decision, and each machine fetches when nobody is at it, verifies every file against its hash, and only then makes it loadable. Expect drift to show for a while, and to clear on its own.

Rolling out a new agent build

Register the build on the control plane, then set a group's channel to this control plane and choose the version. Machines fetch it, verify the hash, restart, and roll themselves back if the new binary fails to report in. Groups left on MDM or by hand are never pushed to; the console records what it expects and reports what it sees.

curl -sk -X POST https://localhost:8452/admin/v1/agent/builds \ -H "authorization: Bearer ADMIN_ID" -H "content-type: application/json" \ -d '{"version":"2026.08.11-1","path":"/path/to/dai-agent","notes":"what changed"}'

What the machine's owner sees

A menu bar icon showing whether the machine is available, working, or waiting, what it has contributed, and a pause button. Pausing writes a file under /Users/Shared, works with the network down, and nothing on the server can clear it. It stops the work and also releases the hold that keeps the machine awake. You will be asked about this; the honest answer is that the button always wins.

Backups

Run ./scripts/backup.sh on a schedule. It captures the certificate authority, the database and the configuration, and skips model weights deliberately: those can be fetched again, and the catalogue's hashes make a re-import verifiable. Restoring moves the existing CA aside rather than overwriting it, and checks the result against a manifest.

When something goes wrong

Every failure seen so far, and what it actually was

What you seeWhat it isWhat to do
the daemon will enrol on first start Normal over SSH. The Enclave will not generate a key in an SSH session. Nothing. Approve the machine when it appears.
Bootstrap failed: 5: Input/output error The old daemon had not finished stopping. It holds a long-poll connection and does not exit instantly. sudo ~/dai/packaging/reload-daemon.sh system com.dai.agent /Library/LaunchDaemons/com.dai.agent.plist
Installer exits and nothing is installed An early step failed. Older versions exited without saying what state they left behind. Re-run the installer. It is safe to run on a working machine and will not disturb the identity.
A deploy appears to succeed but the version does not change The copy did not take, or the daemon was not reloaded. Check the size and date of /usr/local/libexec/dai/dai-agent against the build you meant to install.
A machine enrolled under a name like syn-2600-6c52-… An old agent read its name from reverse DNS during boot and got its own IPv6 address. Fixed in current builds. Rename the row in the database; the identity is unaffected.
A machine goes unreachable for minutes at a time It is asleep. The agent holds the machine awake only on mains power, unpaused; a laptop on battery or with its lid shut still sleeps. Check pmset -g assertions | grep -i dai on the machine. Plug it in.
The menu bar icon never appears The agent was installed but the login session did not pick it up, or the screen is locked. sudo launchctl kickstart -k gui/501/com.dai.menubar, using the console user's uid.
A machine is in the fleet but never gets work Usually presence: harvest machines only take GPU work once locked, and promotion waits five minutes. dai-agent presence on the machine reports the state and what it currently permits.
Requests to the serving API return 503 No machine is both holding the model and free. Check Models for drift, and Machines for presence. A machine in use is not offered interactive work.
com.dai.updater did not unload after 60s An upgrade was in flight. A root process is partway through replacing the binary the uninstaller is trying to delete, so it stops rather than pulling the floor out. Wait for the upgrade to finish, then run the uninstaller again. Nothing was removed.
An uninstall printed ==> stopping and nothing else An old copy of uninstall.sh. It stopped on a failed menu bar bootout — which fails whenever the menu bar job is not loaded — after removing the agent and before removing the identity, and said nothing. Copy the current scripts to the machine and re-run. A --purge that ended this way did not purge: check whether /var/db/dai is still there.
A removed machine still has a root job polling the control plane Also an old uninstall.sh, which did not stop the updater. sudo launchctl bootout system/com.dai.updater; sudo rm -f /Library/LaunchDaemons/com.dai.updater.plist. Current versions do this for you.
A reinstalled machine comes back on the version before last A pending-upgrade marker survived the uninstall. The updater reads it before anything else, sees a deadline long past, and restores the rollback binary over the version just installed. sudo rm -f /var/db/dai/pending-upgrade.json /var/db/dai/dai-agent.rollback, then reinstall. Current versions clear both.

Removing an agent

Give a machine back

ssh -t studio-01.local "sudo ~/dai/packaging/uninstall.sh --purge"

Without --purge the agent stops and the binary and menu bar app are removed, but the machine's identity, its logs and the _dai service account stay behind. Use --purge unless you are about to reinstall on the same machine and want to keep its enrolment.

The updater is stopped first, before the binary is removed, and the script waits for it to actually be gone rather than just asking. That ordering is the point: the updater is a root job whose purpose is to put the agent binary back, so an uninstall that removed the binary while it was still loaded could be undone by the machine itself two minutes later.

If it says the updater did not unload

The script stops, leaves the binary alone and exits non-zero. That means an upgrade was in flight and a root process was partway through replacing the binary you are trying to delete. Wait for it to finish and run the uninstaller again; there is nothing to clean up by hand.

An interrupted upgrade is cleared either way. The pending-upgrade marker and the rollback copy are removed even without --purge, because a marker that outlives its binary is not a record of anything and the next install would act on it — reading it first, finding a deadline long past and no agent reporting in, and restoring the old binary over the version just installed.

Then revoke the machine's certificate, or it remains a fleet member that simply stopped reporting:

curl -sk -X POST https://localhost:8452/admin/v1/nodes/NODE_ID/revoke \ -H "authorization: Bearer ADMIN_ID" \ -H "content-type: application/json" -d '{}'
